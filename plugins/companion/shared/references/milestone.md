# Milestone

## Local meaning

In companion, a Milestone is a substantial, coherent work package under a Project. It owns a meaningful outcome and links directly to Tasks. This local usage differs from a scheduling milestone, which marks an achievement or significant point.
Each newly planned Task has one owning Milestone and links to that Milestone's Project. Preserve existing direct-Project tasks until the user requests reconciliation. Read existing relations before proposing membership changes.

## Discuss before defining

Read project purpose, requirements, existing milestones, and relevant tasks first. Establish the intended outcome, included work, completion criteria, constraints, and boundaries with other milestones. Surface missing information before settling names or scope.

Propose a milestone when work benefits from separate outcome, scope, progress, or dependency control. Small actions belong in Tasks or checklists. Use meaningful work volume, not an arbitrary task count or duration threshold.

Name the result or bounded work package. Add a cycle, application group, or readiness qualifier when useful. For example: `Core application materials ready for tailoring`.

For each proposal, explain:
- Intended outcome and evidence of completion.
- Included work and boundaries with adjacent milestones.
- Relevant existing Tasks and missing work to discuss.
- Priority, timing constraints, and genuine prerequisites when known.

Keep one primary scope home for each piece of work. Reference shared outputs instead of duplicating work across milestones. Give ongoing activities a bounded cycle or review condition before treating them as complete.

## Priority

Use `1. Protected`, `2. Core`, `3. Opportunistic`, and `4. Deferred`. Assess milestone priority independently of Project priority for the current planning horizon.
Read [Work Planning & Execution Control](https://app.notion.com/p/3db0a859ed1f81cf826dfead8fdd5490) for current priority semantics.

## Timing and dependencies

A milestone may be deadline-bound, constrained by another outcome, or flexible. Define scope even when dates are unknown. Preserve unknown dates and surface them as unresolved if active Notion policy requires dates.

Describe the precise predecessor output required by the successor. Distinguish full completion from partial readiness. Preferred order and shared resources alone do not establish prerequisites.
Place dependencies at the narrowest useful level. Some Tasks may proceed while other work in their milestone remains blocked.
Before writing dependencies to Notion, inspect the live schema and check for cycles. Task dependency fields do not prove Milestone dependency fields exist.

## Reference

[PMI: Applying the work breakdown structure](https://www.pmi.org/learning/library/applying-work-breakdown-structure-project-lifecycle-6979) informs outcome-oriented decomposition and the transition from work packages to scheduling.
