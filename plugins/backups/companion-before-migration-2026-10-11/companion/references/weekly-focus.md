# Weekly focus

## Inventory and identify the week

Resolve the selected Projects, review date range and user timezone. Use a stated Monday-to-Sunday assumption when no other week convention is given. Review each selected Project as a whole under [Coverage and effects](working-context.md#coverage-and-effects), even when the user mentions only one outcome. Inventory all Milestones and Tasks, including completed, Deferred and legacy direct-Project records. Then read the relevant bodies, canonical log and dated notes or Resources. Do not expand to unrelated Projects without a reason or user-selected scope.

Build the week's Task set from the union of the prior commitment, deadlines or scheduled work in the period, dated evidence of activity or completion, and earlier overdue or blocked work that affects the commitment. Deduplicate by record identity and retain the reason each Task is included. Distinguish planned, due, worked, completed and carried-over work. A due date is not evidence of execution. A page edit timestamp is not a completion date. If history is unavailable, keep weekly attribution unknown and ask only for the material missing facts.

Read current Project, Milestone and Task priorities separately. Use dated log evidence for historical priorities and commitments. Current properties cannot reconstruct a past week by themselves. Report coverage counts and missing sources before claiming a full review.

## Priority eligibility

For a new weekly commitment, select Tasks only under Milestones with Priority 1, 2 or 3. Priority 4 Milestones retain their Tasks as backlog but contribute no committed Tasks for that week. A priority change during the week does not erase work already done or the original commitment.
Evaluate each Task's Priority separately. Keep Priority 4 Tasks outside the new commitment. Priority 1, 2 or 3 is eligibility, not automatic selection; check readiness, dependencies and capacity. If urgent work sits under a Deferred Milestone, surface the conflict and settle an explicit priority change before committing it. Missing priority or ownership remains unresolved. Do not apply this rule as deletion or as a ban on capturing backlog Tasks.

## Select work with the user

Read current project context, milestone outcomes, relevant Task bodies, deadlines, dependencies, and reported progress. Read calendar constraints when capacity or timing matters.
Discuss which milestone outcomes matter this week and which specific Tasks can advance them. A selected Milestone does not select all its Tasks. Project, Milestone, and Task priorities may differ and may change with the planning horizon.
Account for prerequisites, effort, competing projects, and available capacity. Preserve unfinished work when deferring it. A blocked Protected Task remains important; discuss the prerequisite rather than pretending it is executable.
Keep lifecycle Status, Priority, weekly selection, deadline, and scheduled time distinct. Moving work out of this week's focus does not automatically change its deadline, Status, or parent Milestone.
Reassess remaining work when reality changes. Preserve completed outcomes. Propose changes first; update Notion only on explicit request.

## Weekly entries in the project log

Use the canonical project log and Progress log tab under [Capture and evidence](capture.md). Save a weekly review only when requested, inside the capture day's `YYYY-MM-DD` toggle. Record the reviewed period and next week's period separately.
Keep an entry short: intended outcomes, links to selected Milestones and Tasks, deferred work and reasons, then dated changes or actual results when known.
Link canonical work records instead of copying task lists or maintaining a second completion checklist. Historical entries record what was selected and why; current records hold current state. Live linked views are for current interaction, not immutable historical snapshots.
When asked to change a Task from a log discussion, update the canonical Task and record the decision only where useful. A log entry alone does not update Task properties.
Do not create a journal, scaffold future weeks, or move deadlines automatically.

## Weekly review and commitment

Compare the prior agreed focus with this week's outcomes before choosing new work. Follow [Owner progress and recorded state](working-context.md#owner-progress-and-recorded-state). The owner's clear completion statement takes precedence over stale Status; separate that confirmation from independently inspected evidence. Keep Task completion distinct from Milestone completion. Propose exact Status and closure actions, plus any Priority changes; weekly selection alone changes neither.

Select a finite set of canonical Tasks and intended outcomes for next week. Resolve each Task's owning Milestone, matching Project, concrete deadline, Priority and completion criteria under [Task](task.md). Support the user's task drafts; create new records only when requested. Leave incomplete candidates outside the settled commitment until the missing decisions are resolved.

Account for every Task agreed in the discussion: committed, conditional, deferred or unresolved. Resolve the intended week from explicit dates and context; clarify contradictory “this week” and “next week” wording. Propose a concrete deadline within that week for each committed Task. When only weekly completion matters, propose the last day of that week as the target and obtain agreement before writing. Preserve hard deadlines. The user places work on individual days and calendar times; a deadline is not a scheduled session.

State what is deferred and why. Agree the condition for admitting additional work, such as replacing a selected Task or resolving a prerequisite. Keep the original commitment in history. Record later changes with their date and reason rather than silently rewriting what was agreed. Consider capacity across named Projects, then save each Project's own review in its own log.

The saved review contains the review period, prior focus, outcomes and agreed property changes, next week's bounded commitment, deferred work, open decisions and canonical links. Keep enough dated context to understand the decision if live Task properties change. Link the latest review from the Project tab and summarize the agreed next-week focus there. A proposal remains a proposal until the user requests saving it.
