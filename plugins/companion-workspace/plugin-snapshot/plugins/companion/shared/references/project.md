# Project

Required fields: `Areas`, `Due Date`, `Status`, and `Priority`.

- `Areas`: one specific subarea selected by the user. Ask for their selection when missing or ambiguous.
- `Due Date`: the project's temporal boundary. Distinguish the stored range from individual deadlines and calendar sessions. Surface missing dates instead of inventing them.
- `Status`: actual lifecycle state. Read valid values from the live schema. Scheduled work alone does not prove progress or completion.
- `Priority`: treatment in the relevant planning horizon. Read [Work Planning & Execution Control](https://app.notion.com/p/3db0a859ed1f81cf826dfead8fdd5490) when assessing priority. Use `1. Protected`, `2. Core`, `3. Opportunistic`, and `4. Deferred`.

The description explains purpose and intended outcome in one or two plain sentences. Keep transient progress in the Overview.
Use the Overview for context and Current direction. Summarize relevant milestones by state, result and next step or limit. Avoid repeating full task lists. Use an Evidence map for source navigation when the project needs one; follow [Research context](research.md) for local research sources. Discuss a Catalogue before adding it.
Keep context distinct from execution records. Read tasks, milestones, notes, and resources from existing objects. Resolve their actual schema and meaning before structural proposals.
Tabs and filtered database views are presentation, not new object types. Keep proposed layouts separate from accepted definitions.

## Overview presentation

Start with purpose and current focus. Separate Main focus, Supporting work and Open decisions when those distinctions help the reader.
Organize progress around existing Milestones. Resolve their identities and use native Notion mentions as headings.
Use separate list items with bold labels for Status, Outcome, Current, Next and Sources. Add Blocker, Dependency or Limit only when relevant. Use Result for completed work. Keep enough explanation within each item to convey its meaning. Combine or omit labels when the content is simple; keep unknown state explicit.
Read Status from the Milestone property. Keep it separate from Current and Blocker: an In Progress Milestone can be waiting for parts. If the property is unavailable, state that its status needs confirmation. Use Sources only when relevant evidence or navigation is available.
Highlight labels and a few decision-critical phrases, such as a blocker or required confirmation. Keep ordinary explanation in plain text so highlights remain useful. Prefer this readable list to a dense status table or an uninterrupted paragraph.
Place active work first. Keep completed foundations accessible in a toggle when useful. Link a small number of relevant source files beside the claims they support. Label a Goal or index as a navigation source rather than a result report. Multiple sources can support one Milestone, and one result can inform several Milestones; inspect the mapping instead of assuming it from names.
Keep the Overview as a dated current synthesis, the Evidence map as source navigation, and a Progress log as dated history. Do not imply automatic synchronization. Attribute owner updates and mark unverified or conflicting state. A presentation change does not change Milestone status, priority, ownership or completion.
Follow [Capture and evidence](capture.md) for historical log entries and the tab's latest review, agreed focus and pending attention.
