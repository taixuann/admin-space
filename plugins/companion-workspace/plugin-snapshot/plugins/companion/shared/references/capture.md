# Capture and evidence

## Canonical log

Use one Project-related Resource page as the default Progress log destination. Apply [Resource status and placement](resources.md#status-and-placement). Draft means provisional content; Active means a log in use. Keep processing state separate from Resource status. Do not change status merely because an entry was captured or processed.

Keep one toggle per capture day, titled exactly `YYYY-MM-DD`, newest first. Reuse the existing date toggle for same-day entries. Place Initialization, captures and Weekly review inside it. State the review period inside a weekly entry. Create entries only when there is information to retain. Keep small captures in the existing page. Propose a separate Resource only when the material needs independent retrieval or links.

Include the update, attribution, source link, capture date and any known event date. Include a decision and its reason only when settled. For an inspected GitHub snapshot, retain the repository, file and inspected commit when available. Label branch links as current navigation. Preserve source evidence and add dated corrections rather than silently rewriting history.

## Pending attention

Use the Project's Progress log tab to show Latest weekly review, Next week's focus, Needs attention and a link to Project history. Link the canonical review and show only its agreed focus. If no review or commitment exists, state that clearly. Each pending item states the open question or required check and links to the canonical capture. Deduplicate pointers to the same issue. A notable result with no unresolved action belongs in the log and does not require a pending reminder.

Use simple wording such as Needs confirmation or Needs source check. Keep it in content unless a schema change is requested. The user reads and decides when to process items; capture does not run a recurring review.

After an explicit resolution request, record the conclusion and date in the canonical log. Verify it, then remove only the resolved pending pointer. If the conclusion cannot be saved, retain the pointer. Resolving a reminder does not delete the Resource or its history.

## Evidence map

Use the Evidence map as navigation to canonical Notion Resources/References and relevant external source files. For each useful group, name the related Milestone or question, link the source and explain briefly what it helps establish or understand.
Start with a useful project entrypoint, then group selected sources by the question or work they support. Use bold source labels and short descriptions of what to read there. Mention resolved Notion Milestones natively; use external links for GitHub files. Keep navigation indexes distinct from result reports, and state material boundaries beside the relevant source.
Inspect each new source before describing its contents. A source description is not independent scientific validation. Include existing Resources only when their identity and purpose are known; leave empty categories out. Preserve useful existing links and unresolved source differences, or present their removal explicitly in the proposal. Date the layout update separately from the last actual source comparison.

Distinguish context, dated snapshots, research results and source navigation as presentation groups, not new database types. Link directly to GitHub evidence when no distinct Notion synthesis is needed. Follow [research source rules](research.md). Reuse existing objects and preserve source ownership rather than maintaining duplicate results or log entries.

Overview summarizes current state. The Evidence map locates sources. The Progress log page retains history. The Progress log tab surfaces the latest weekly review, agreed focus and pending attention. Update only the destinations included in the user's request.
